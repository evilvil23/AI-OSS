## v0.01 备份功能需求文档
### 1. 总体描述

实现文件备份还原模块，支持**热备份**，提供完整备份、增量备份，支持定时任务、备份生命周期管控、冻结保护，保证数据可备份、可还原、可自动清理。

### 2. 功能需求

#### 2.1 备份源与存储配置
1. 以任务的形式组织备份
2. 支持选择多个源文件 / 目录作为备份对象；支持配置排除文件 / 目录规则。
3. 可自定义备份文件存放目录；目录不存在自动创建，无读写权限直接报错。
4. 支持主动选择任务的备份包是否压缩
5. 通过选择备份任务的备份历史实现还原操作（支持只还原部分文件或全部还原，支持选择还原到原位置或还原到指定位置）
6. 支持在任务执行后发送执行结果到邮箱，来确认任务的完成情况
7. 可以对数据库等文件实施热备份，可以读取正在被其它程序独占打开的文件
8. 可以对USB移动存储设备进行实时监控，当移动存储设备插上时自动执行备份或同步（**USB 设备需要预先绑定到备份任务**，不能任意 U 盘插入就执行备份；防止陌生 U 盘插入误触发。）
9. 定时同时支持**简单周期（日 / 周 / 月） + Cron 表达式**，简单周期内部转 Cron 存储。
10. 任务自动触发模式：实时、定时、间隙或手动地启动任务
11. 元数据存储在元数据在 SQLite中

~~~sql

-- 备份任务表
CREATE TABLE backup_task (
    task_id INTEGER PRIMARY KEY AUTOINCREMENT,
    task_name TEXT NOT NULL,
    source_paths TEXT, -- json数组
    exclude_patterns TEXT, -- json数组
    output_dir TEXT,
    enable_compress BOOLEAN,
    compress_level INTEGER,
    trigger_mode TEXT, -- manual/timer/realtime/interval
    cron_expr TEXT,
    usb_device_id TEXT, --绑定的USB设备标识，为空不监控usb
    max_backup_count INTEGER,
    max_backup_size TEXT,
    enable_email_notify BOOLEAN,
    smtp_config TEXT,
    enabled BOOLEAN,
    create_time DATETIME
);

-- 备份历史元数据表
CREATE TABLE backup_history (
    backup_id INTEGER PRIMARY KEY AUTOINCREMENT,
    task_id INTEGER REFERENCES backup_task(task_id),
    backup_type TEXT, -- full / incremental
    start_time DATETIME,
    end_time DATETIME,
    store_path TEXT,
    total_size INTEGER,
    is_frozen BOOLEAN DEFAULT 0,
    status TEXT, -- success / partial / failed
    parent_backup_id INTEGER, --增量依赖父备份id
    hash_sum TEXT,
    remark TEXT
);

CREATE INDEX idx_task_id ON backup_history(task_id);
CREATE INDEX idx_frozen ON backup_history(is_frozen);

~~~

#### 2.2 备份类型

1. **热备份**：程序运行时执行备份，无需停止业务；对正在写入的文件不强制锁文件，给出风险提示。
2. **完整备份**：复制全部源数据，备份包独立，可直接还原。
3. **增量备份**：仅备份变更文件；依赖已有完整备份才可创建；支持完整还原；还原时校验整条备份链完整性，链损坏拒绝还原。

#### 2.3 定时任务

1. 支持手动触发备份，也支持定时任务；支持间隔周期、Cron 表达式。
2. 任务可启用 / 禁用；同一任务未执行完毕时再次触发，直接跳过本次执行。
3. 记录任务执行历史：时间、备份类型、成功 / 失败、错误信息。（提供单独的备份日志文件backup.log）

#### 2.4 备份生命周期管理

1. **备份配额**：配置最大备份数量、备份总最大存储空间。
2. **冻结备份**：可将备份标记为冻结；冻结备份不计入备份数量、不计入存储空间统计；自动清理逻辑不会删除冻结备份；仅允许用户手动删除。
3. **自动清理规则**：备份完成后执行清理；仅处理非冻结备份；按最早优先删除，直到满足数量、大小双阈值；绝不触碰冻结备份。

#### 2.5 还原功能

1. 完整备份、增量备份均支持还原；支持还原至原路径或自定义目标目录。
2. 还原冲突策略可选：询问用户、直接覆盖、跳过、重命名旧文件。
3. 还原前校验备份完整性；支持浏览备份内文件列表；还原后做文件校验。

#### 2.6 校验与异常处理

1. 备份完成生成校验哈希，标记备份完好 / 损坏状态。
2. 备份前预检查：源目录可读校验、备份磁盘剩余空间校验。
3. 同一时间只运行一个备份任务；备份中途失败，丢弃不完整备份产物，记录错误日志。
4. 提供操作日志：备份、还原、清理记录，支持查看、导出日志。

#### 2.7 备份元数据

每份备份保存元信息：备份 ID、备份类型、起止时间、源路径、存储路径、大小、是否冻结、状态、依赖备份 ID（增量）、校验哈希、用户备注。

### 3. 非功能需求

1. 并发约束：禁止同时运行多个备份任务。
2. 容错：源文件被占用 / 正在写入，做标记，不直接中断整个备份。
3. 风险提示：热备份场景提示高频写入文件存在数据不一致风险。

### 4. 禁止行为

1. 自动清理逻辑**严禁删除冻结备份**。
2. 无完整备份时禁止创建增量备份。
3. 不允许直接还原损坏的备份链。

## v0.21 AI 管家与知识库需求文档

### 1. 总体描述

在现有 NAS 之上实装 **AI 管家 + AI 知识库（RAG）+ Ollama 全生命周期管理 + 智能家居控制**：服务端自动管理 Ollama 进程与模型加载，按本机硬件自适应选择模型与推理参数，提供模型管理 / 状态查询 / 局域网调用（OpenAI 兼容端点）能力，支持单机与主备双机两种部署形态，并接入 HomeAssistant 实现设备查询与控制。技术栈 Go 1.25 + 字节 Eino 框架（`github.com/cloudwego/eino`）+ Ollama 本地推理，沿用现有 Gin 分层架构，前端无感。

### 2. 功能需求

#### 2.1 Ollama 生命周期管理

1. 服务端启动时自动检测 Ollama 是否运行（Ping `/api/tags`）；未运行且开启托管（`[ai.ollama].managed=true`）时后台拉起 `ollama serve`（记录 PID），等待就绪（超时可配）后按硬件预设加载默认模型（空对话预热触发）。
2. 优雅关闭时先以 `keep_alive=0` 调用 `/api/generate` 卸载模型释放显存 / 内存，再停止 Ollama 进程——**仅停止本服务拉起的实例**，绝不杀掉用户自启的 Ollama。
3. 服务重启时接管上一任服务实例（凭 PID 文件识别）；用户自启实例仅检测不做进程管理。
4. 提供状态查询 API：Ollama 进程状态（托管 / 自启 / 未运行）、已加载模型（等价 `ollama ps`）、显存 / 内存占用。
5. 跨平台：Windows 用 `os/exec` 后台进程 + PID 记录；Linux 同样直接 exec（可退化为 systemd）。

#### 2.2 硬件自适应与模型调优

1. 启动时检测：NVIDIA GPU 是否存在及总显存（nvidia-smi）、总内存、CPU 型号。
2. 判定规则（config.toml `[ai.tune]` 可整体覆盖，配置优先、禁止写死）：
   - 有 NVIDIA GPU 且显存 ≥ 8GB → `deepseek-r1:7b`（DeepSeek-R1-Distill-Qwen-7B，官方默认 Q4_K_M 约 4.7GB 可全量进 12GB 显存），预设 `num_ctx=8192`、`keep_alive=-1`（常驻）、`num_parallel=2`；
   - 无 GPU 或显存 < 8GB（如 N100）→ `qwen3.5:9b`（需求中的 `qwen3.5-7b-instruct:q4_K_M` 在 Ollama 官方库不存在该精确 tag，取最接近的 7B~9B 级 Q4_K_M），预设 `num_ctx=4096`、`keep_alive=5m`、`num_parallel=1`；低内存设备（< 12GB）兜底回落 `default_model` 避免内存挤占。
3. 调优参数保存为「硬件配置预设」，实际生效值（含来源 config/auto）记录到日志与状态 API，便于核验。

#### 2.3 Eino 框架集成

1. 引入 `github.com/cloudwego/eino`，将 Ollama 直连调用重构为 Eino ChatModel 组件（实现 `ToolCallingChatModel` 接口），工具调用走 Eino Tool 协议与 ToolsNode。
2. 保持现有 AI 服务对外 API（对话 / 流式 / 会话 / RAG 注入）行为不变，前端无感。

#### 2.4 服务端模型管理（仅主人 / 管理员）

1. 模型列表（含量化信息）、拉取模型（`ollama pull` 进度可查）、删除模型、查看 / 调整推理参数（`num_ctx`、`temperature`、`keep_alive` 等）。

#### 2.5 局域网调用

1. 支持配置 Ollama 绑定 `0.0.0.0:11434`（拉起时注入 `OLLAMA_HOST`），供局域网其他设备 / 应用调用。
2. smart-nas 提供 OpenAI 兼容代理端点 `POST /api/ai/v1/chat/completions`（走 smart-nas JWT 鉴权，model 缺省时自动补当前生效模型），并支持直连 Ollama 原生 `/v1`。
3. 局域网暴露的 AI 接口必须走既有 JWT 鉴权；绑定地址与防火墙放行在文档中说明。

#### 2.6 部署模式（single / dual 主备双机，可选开启）

1. 配置项：`mode`（single / dual，默认 single）、本机角色（`role`：primary / auxiliary，dual 生效）、远端 Ollama 地址、自动切换开关、探测间隔。**三种形态互不依赖，切换只改配置，重启或热重载生效，不涉及代码改动。**
2. **单机模式**：本机独立运行，按 2.2 硬件自适应选择本机模型（大主机即高级模型、N100 即低配模型），RAG 使用本机索引。
3. **双机模式**：
   - 主服务（primary，通常 N100 常驻）：按本机硬件选低配模型，RAG 默认开启，作为知识库与模型服务端；
   - 辅助机（auxiliary，通常大主机）：启动时探测远端 Ollama，可达则自动切换为远端模型（卸载本地模型释放资源）并调用主服务侧 RAG（**辅助机不建立独立向量库**）；远端不可达则降级回本机模型并记录告警；运行中周期探测自动双向切换。

#### 2.7 HomeAssistant 智能家居接入

1. 实现 HomeAssistant REST API 客户端：实体列表（按 domain 过滤）、状态查询、调用服务（开关 / 亮度 / 温度等）。
2. 注册为 AI 工具（`ha_list_devices` / `ha_get_state` / `ha_call_service`）并入现有工具注册表，AI 对话即可控制设备；危险操作提示二次确认。
3. 当前无 HA 设备：交付连接配置项 + 连通性自检（`GET /api/` + token 校验）；未启用 / 自检失败 / 无设备时明确降级（不注册工具，对话提示暂不支持），接入逻辑以单元测试 + Mock 响应验证。

### 3. 非功能需求

1. 模型选择与调优参数可配置（config.toml 优先），自动检测结果仅作默认值。
2. Ollama 拉起超时、预热开关、绑定地址、部署模式、HA 地址令牌均可在 config.toml 配置并支持热更新。
3. 现有对外 API 与前端行为不变；AI 改造为内部实现替换。
4. 不引入新的向量库服务（沿用 chromem）；不做 HA 高级自动化编排（沿用现有 iot/automation）；不做多用户配额 / 计费 / 限流。

### 4. 禁止行为

1. 优雅关闭**严禁停止用户自启的 Ollama 进程**（仅限本服务拉起或接管的实例）。
2. 双机模式辅助机**禁止重复建立独立向量库**（RAG 统一走主服务）。
3. 局域网 AI 接口禁止裸奔（必须走 JWT 鉴权）。

## v0.23 AI 设置与主辅机模式需求文档

### 1. 总体描述

在 v0.21 AI 管家基础上补齐**设置与模式体验**：网页设置中开放 AI 部分（启动模型主动选择、机器模式选择、服务端地址配置），机器模式支持 `auto` 自动判定（配置了服务端地址且可达 → 辅机；未配置或不可达 → 服务端），配置文件与网页设置页双通道可配；需重启才能生效的设置项修改后提示用户并**自动重启服务**；主页新增 **AI 对话窗口**与**智能家居设备管理**页签。沿用现有 Gin 分层与前端模板 + 静态资源结构。

### 2. 功能需求

#### 2.1 AI 设置页（网页「AI → 设置」，仅主人 / 管理员）

1. **启动模型主动选择**：下拉选择默认对话模型（数据源为模型列表接口），保存后热更新生效，无需重启。
2. **机器模式选择**：`auto`（自动判定，默认）/ `server`（服务端）/ `auxiliary`（辅机），对应 `config.toml [ai.deploy].mode`（auto/server/auxiliary）。
3. **服务端地址**：辅机模式连接的远端 Ollama 地址（host:port 或 URL），写入 `[ai.deploy].remote_host`。
4. 推理参数（num_ctx / temperature / keep_alive / num_parallel）沿用 v0.21 热更新能力。
5. 同一套设置既可通过 `config.toml` 配置，也可通过网页设置页配置（网页保存持久化回 config.toml）。

#### 2.2 机器模式 auto 自动判定

1. 启动时解析：`mode=auto` 且配置了服务端地址（remote_host）且**可达**（Ollama Ping，5 秒超时）→ 以**辅机**模式启动；未配置地址或**不可达** → 以**服务端**模式启动，判定结果记录日志。
2. 判定结果仅存在于运行态（持久化配置保留 `auto` 原值）；运行中不因断连切换身份（不摇摆）。
3. 配置热更新回调中同样先做 auto 解析再下发 AI 服务。

#### 2.3 重启提示与自动重启

1. `PUT /api/ai/settings` 响应携带 `need_restart` 数组：对比保存前后配置，列出**启动期装配**字段（`ai.deploy.mode` / `ai.deploy.role` / `ai.deploy.remote_host` / `ai.deploy.remote_api` / `ai.ollama_host` / `ai.embedding_model`）中被修改的项；结果永不为 nil（JSON 输出 `[]`）。
2. 前端保存时若 `need_restart` 非空：提示「某项设置需重启服务才能生效」，用户确认后提示「服务重启后请刷新页面」，随后自动调用重启；取消则提示已保存、下次重启生效。
3. 新增 `POST /api/admin/restart`（仅主人/管理员）：进程级**优雅重启**——先走优雅退出（卸载模型、停托管 Ollama、停调度器），再自动拉起新进程接力（Windows 父进程接力）；通道缓冲 1，重启进行中重复请求返回 409，未注入重启通道返回 503。
4. 前端重启后轮询 `/healthz`，恢复即提示刷新页面（超时降级为手动刷新提示）。

#### 2.4 主页 AI 对话窗口与智能家居管理

1. 主页导航新增 **AI** 页签：左侧会话列表（新建/切换/删除），右侧流式对话窗口（SSE 逐字输出、可中断），工具栏含模型切换、模型管理与设置入口。
2. 主页导航新增 **智能家居** 页签：HomeAssistant 设备网格（按 domain 展示名称与实时状态），开关类设备可直接点击控制；底层为 `GET /api/ai/ha/status`、`GET /api/ai/ha/devices`、`POST /api/ai/ha/service` 三个设备管理接口。
3. 未启用 HA 或连接失败时页面给出配置指引（需 `[ai.homeassistant]`），不阻塞其他页签。

### 3. 非功能需求

1. 需重启字段与热更新字段的边界以「是否启动期装配」为准，判定逻辑集中在服务端（`aiNeedRestartFields`），前端不做硬编码。
2. 重启过程必须复用现有优雅退出链路，不得跳过模型卸载与 Ollama 托管进程清理。
3. 模式判定、重启端点、HA 设备接口均需单元/链路测试覆盖。

### 4. 禁止行为

1. **禁止**在 auto 判定后把结果写回持久化配置（保留 auto 原值）。
2. **禁止**在运行中因远端断连自动切换机器身份（auto 仅启动期判定一次）。
3. 重启接口**禁止**对普通用户开放；重启过程中**禁止**跳过优雅退出步骤。

## v0.24 Windows 系统调用重构需求文档

### 1. 总体描述

将项目内全部 Windows `kernel32.dll` 调用从**原生 `syscall.NewLazyDLL`**
重构为 **`github.com/ebitengine/purego`**（免 cgo），统一函数调用语义，
消除裸 `proc.Call(uintptr(unsafe.Pointer(...)))` 调用方式；依赖下载到本地
vendor，保持离线构建能力。

### 2. 功能需求

#### 2.1 purego 封装范围

1. **系统状态采集**（`internal/util`）：`GlobalMemoryStatusEx`（内存）、
   `GetTickCount64`（运行时长）、`GetSystemTimes`（CPU 占用）、
   `GetDriveTypeW` / `GetDiskFreeSpaceExW`（磁盘枚举与容量）、
   `GetFileAttributesW`（隐藏/系统文件检测）、`GetVolumeInformationW`（卷标/序列号）。
2. **备份模块**（`internal/backup`）：`GetDriveTypeW` / `GetDiskFreeSpaceExW`
   （备份前磁盘空间预检）、`GetVolumeInformationW`（USB 可移动设备卷标/序列号枚举）。
3. **AI 硬件自适应**（`internal/ai/hardware`）：`GlobalMemoryStatusEx`（总物理内存检测）。
4. DLL 句柄经 `golang.org/x/sys/windows.LoadLibrary` 获取（purego 在 Windows
   不提供 `Dlopen`，Windows 系统 DLL 官方推荐用 x/sys/windows 加载），
   函数地址经 `purego.RegisterLibFunc` 绑定为 **Go 类型化函数指针**，
   参数/返回值以类型化签名声明，由 purego 完成寄存器/栈参数编排。

#### 2.2 降级与安全

1. `kernel32.dll` 加载失败或函数符号缺失时，函数指针保持 nil（注册 panic 被捕获），
   调用方按「该能力不可用」返回安全零值，**不影响服务启动**。
2. UTF-16 编解码以 `unicode/utf16` 实现（`utf16FromString` / `utf16ToString`），
   不再依赖 `syscall.UTF16PtrFromString` / `syscall.UTF16ToString`。
3. 跨平台：Windows 为真实实现，非 Windows 平台（`//go:build !windows`）提供
   同签名桩实现，返回安全零值。

### 3. 非功能需求

1. purego 依赖（`github.com/ebitengine/purego`）必须下载到本地 vendor，
   离线 `go build ./...` 与 `go test ./...` 均可通过。
2. 行为兼容：系统状态 / 磁盘列表 / 隐藏文件屏蔽 / USB 设备枚举 / AI 硬件检测
   的对外行为与重构前一致。
3. 进程属性（`os/exec` + `syscall.SysProcAttr`）与信号处理等非 DLL 加载场景
   不在重构范围。

### 4. 禁止行为

1. **禁止**在 Windows 平台调用 purego 的 `Dlopen`（该 API 仅 Unix 可用，
   会编译失败）。
2. **禁止**保留原生 `syscall.NewLazyDLL` / `windows.NewLazySystemDLL` 的 DLL 加载残留。

## v0.26 配置与设置完善需求文档

### 1. 总体描述

完善配置与设置链路：AI 能力增加**可开关的总闸**，并对其依赖（Ollama 与所需模型）做
启动预检，缺失时降级而非阻断服务；配置写入改为**映射表（调度表）**并**保留 config.toml 注释**；
AI 设置并入统一的「保存设置」，需重启项以**布尔标志**表达；修复 `go run` 场景下
终端 Ctrl+C 无法终止服务进程的问题。

### 2. 功能需求

#### 2.1 AI 功能总开关

1. `[ai]` 新增 `enabled`，**代码默认 `false`**（默认关闭）。
2. 关闭时服务启动整体跳过 AI 初始化并记录日志，其余功能不受影响。
3. AI 禁用时前端 AI 页签给出**差异化禁用提示**（点击菜单弹出自动消失提示、输入区置灰），
   设置页开关仍可打开，以便下次启动启用。

#### 2.2 本地部署启动预检

1. 开启 AI 且为本机推理（`single` / `dual+primary`）时，启动依次检查：
   ① Ollama 是否可用（未安装 / 未运行 / 拉起失败）；② 实际使用的**对话模型**是否已拉取。
2. 任一缺失：控制台打印 `[AI] 预检失败：…`（含可操作的修复建议），
   **运行态禁用 AI 并继续启动服务**，不得阻断其他功能。
3. **RAG 向量模型缺失只降级知识库**（提示「对话功能不受影响」），不停用 AI；
   其初始化以「本机 Ollama 就绪」为前提，AI 模型无法启动时不加载向量模型。
4. 提示中的模型名必须与**实际使用的模型一致**，不得把向量模型误作对话模型报出。

#### 2.3 配置项调度表

1. `setByPath` 由巨型 `switch` 改为映射表 `configSetters`（路径 → setter），
   新增配置项只需登记一行，调度逻辑不变。
2. 修复 `storage.trash_path` 分支漏置 `ok=true` 导致「解析成功仍报无效配置值」的缺陷。
3. 未登记的路径仍按「未知配置项」报错（白名单语义不变）。

#### 2.4 配置写回保留注释

1. 设置页保存 / 配置热更新落盘时，**必须保留 `config.toml` 中的注释、空行与缩进**。
2. 保留策略：以序列化结果为权威键值，仅替换原文件中对应键的值行；
   字符串内的 `=` / `#` 不得被误判为分隔符 / 注释。
3. 原文件缺失的新键按所属分段追加；原文件不存在时回退为完整覆盖写。

#### 2.5 统一保存与待重启标志

1. AI 设置并入设置页统一的「保存设置」按钮，不再单独提供保存入口。
2. 以**布尔标志**表示「存在已保存但需重启才生效的变更」，前端据此展示提示条与「立即重启」按钮。
3. 标志在保存启动期装配项（`ai.enabled` / `ai.ollama_host` / `ai.embedding_model` /
   `ai.deploy.mode|role|remote_host|remote_api`）时置位，**服务重启后自动重置**。

#### 2.6 进程退出可靠性

1. `go run` 启动场景下，终端 Ctrl+C 后服务进程必须随之退出，不得残留并占用端口。
2. 关闭流程需有兜底：关闭期间再次收到退出信号立即强制退出；关闭总超时后强制退出。

### 3. 非功能需求

1. 预检失败不得阻断服务启动；所有降级路径均需给出可操作的日志提示。
2. 配置写回失败或原文件不可读时，必须回退到可用落盘方式（不丢配置）。
3. AI 关闭 / 禁用状态下，备份、文件、播放、智能家居等其余功能完全不受影响。
4. `go build ./...` / `go vet ./...` / `go test ./...` 全部通过。

### 4. 禁止行为

1. **禁止**因 AI 预检失败而回写或篡改用户持久化配置（仅作用于运行态）。
2. **禁止**因 RAG 向量模型缺失而停用整个 AI 功能。
3. **禁止**直接以 `toml.Marshal` 结果覆盖写 `config.toml`（会丢失注释）。
4. **禁止**在非 `go run` 场景（直接运行编译产物 / 服务管理器启动）启用父进程看门狗导致误退出。
